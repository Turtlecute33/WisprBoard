### TURTLEBOARD-OPT-02: Stop the per-vsync pulse redraw while live audio drives the meter
- **What**: While a dictation records, AiPulseView runs an infinite ValueAnimator. Its update listener calls invalidate() on each vsync (60-120 frames/s on the Pixel 9 Pro XL). The 80 ms ticker also redraws the meter through setAmplitude(). When audio drives the bars (level > 0.01), the pulse is only 15 % of the bar height. So the vsync redraws add no visible information over the 12.5/s ticker redraws. The IME window renders at the display rate for the full recording (15-300 s).
- **Where**: app/src/main/java/helium314/keyboard/latin/voice/AiPulseView.kt:41-44 (startPulse() update listener); AiPulseView.kt:85 (onDraw() pulseWeight); app/src/main/java/helium314/keyboard/latin/voice/RecordingOverlayView.kt:132 (showRecording()), :161-186 (startTicking())
- **Change**: In the startPulse() update listener, keep `pulsePhase = it.animatedValue as Float`, but call invalidate() only when `level <= 0.01f`. This is the same threshold that onDraw uses to give the pulse full weight. Do not change RecordingOverlayView or onDraw.
- **Benefit**: While audio or room noise drives the meter (most of a cloud dictation), the overlay redraws at the 12.5/s ticker rate, not at the display rate. On the other vsyncs the UI thread and RenderThread do no traversal or draw, and the panel can leave 120 Hz. The animator callback still runs on each vsync, but it only sets a float. In true silence (level <= 0.01, often on the on-device engine) the pulse redraws at vsync as it does now. The frame counts are estimates from the code. Nobody measured them.
- **Evidence**: AiPulseView.kt:37-45: ValueAnimator.ofFloat(0f,1f), repeatCount INFINITE, and the listener sets pulsePhase and calls invalidate(). RecordingOverlayView.kt:132 calls startPulse(). :136 calls startTicking(), which posts itself again every 80 ms (:181) and calls setAmplitude() -> invalidate() (AiPulseView.kt:70). LatinIME.java:694-697 and :1459-1465 always set telemetryProvider before showRecordingOverlay(), so the ticker runs for the full recording. setAmplitude() has one caller (RecordingOverlayView.kt:168), so the wait pulse (transcribing, Text Fix, Translate) keeps level == 0 and does not change. - **Safety**: Only the drawing of one custom view changes. No storage, preference key, schema, network or key-handling change, and no dependency. AiPulseView.kt and RecordingOverlayView.kt:132 come from 0a0ad1c8 (Release 7.9.0), which has no 'Report:' line. ### TURTLEBOARD-OPT-05: Do not cache a clip that the database refused to insert
- **What**: SQLiteDatabase.insert catches SQLException (for example SQLiteFullException) and returns -1. insertNewEntry does not check this and still adds the clip to the in-memory cache with id -1. The fork's Compose clipboard panel uses the clip id as the lazy-list key. Two failed inserts of different texts in one process give two cache entries with id -1. When the panel opens, or when search finds both, Compose throws IllegalArgumentException 'Key -1 was already used' and the IME process crashes. A backup restore whose pinned-clip inserts fail (addPinnedClip goes through insertNewEntry) does the same in the pinned row.
- **Where**: app/src/main/java/helium314/keyboard/latin/database/ClipboardDao.kt:82-93 (insertNewEntry); app/src/main/java/helium314/keyboard/keyboard/clipboard/ClipboardPanel.kt:139 (BrowseLayer, `items(listed, key = { it.id })`); ClipboardPanel.kt:240 (PinnedRow, `items(pinned, key = { it.id })`); ClipboardPanel.kt:701 (search, `items(results, key = { it.id })`)
- **Change**: In insertNewEntry, add `if (rowId == -1L) return` after `val rowId = db.writableDatabase.insert(TABLE, null, cv)` at line 87. Nothing else changes.
- **Benefit**: The keyboard does not crash when the clipboard panel opens after failed clip inserts (full disk or an SQLite error). The cache then holds only rows that are in the database, which is also what the next process start loads. Pin, delete and edit cannot act on a phantom id -1 row. The trigger is rare: two failed inserts of different texts in one process.
- **Evidence**: ClipboardDao.kt:87-90 builds ClipboardHistoryEntry(rowId, ...) and calls cache.add with no check on rowId (upstream c56c5715). ClipboardHistoryManager.fetchPrimaryClip:66 -> addClip -> insertNewEntry runs on each primary-clip change. addClip removes duplicates by text only (line 56), so two different texts that both fail give two id -1 entries. ClipboardPanelState.setClips (ClipboardPanelState.kt:140-143) maps the cache 1:1. pinned, listed and searchResults have no distinct step. The keyed lazy lists came with the fork's Material 3 panel in a0db63f5 (7.5.0).
- **Safety**: No change to the CLIPBOARD schema, the columns or the stored rows. The change only skips caching a row that the database did not write. The lines come from upstream c56c5715, and line 92 from a0db63f5. Neither is a 'Report:' commit. The locked-device clipboard block (21a82527) is in ClipboardHistoryManager and LatinIME and does not change. No dependency.
- **Verification**: The stability lens confirmed the path and that nothing removes duplicates by id. Separate privacy note, not part of this change: the framework insert() logs 'Error inserting ' + ContentValues, which puts the clip text in logcat. insertOrThrow in a try/catch would also stop that log, for about +3 lines. Verify: a unit test that makes insert fail (read-only database) and checks that the cache stays empty, or a code read, because no clipboard DAO test exists today.

### TURTLEBOARD-OPT-07: Always give the recording watchdog the recorder's completion
- **What**: watchForSelfAbortedRecording installs the watchdog only if AudioRecorder.completionOrNull() is not null. That getter returns null as soon as recordingJob is null, and the IO coroutine sets recordingJob = null in finalizeOutputFile and cleanupRecordingFailure. When the first read fails at once (a failed startRecording(), ERROR_DEAD_OBJECT, or a write IOException), the loop can end before the main thread finishes state = RECORDING and onRecordingStarted. Then no watchdog is installed, and state stays RECORDING with no microphone. The overlay shows 'Recording...' with a frozen timer. The next key press is swallowed as 'stop recording' and ends with 'no audio' instead of 'recording interrupted'.
- **Where**: app/src/main/java/helium314/keyboard/latin/voice/AudioRecorder.kt:134 (completionOrNull); AudioRecorder.kt:421 (finalizeOutputFile) and :464 (cleanupRecordingFailure); app/src/main/java/helium314/keyboard/latin/voice/VoiceInputManager.kt:274-276 and 290-291 (watchForSelfAbortedRecording)
- **Change**: Change the getter to `fun completionOrNull(): Deferred<File?>? = completion` and update its KDoc. VoiceInputManager makes a new AudioRecorder for each session (VoiceInputManager.kt:250-256), so completion always belongs to the running session. It is null only if start() failed before line 212, and then VoiceInputManager returns before the watchdog. The watchdog already ignores a completion that a normal stop owns (VoiceInputManager.kt:296 checks the recorder identity, state and isStopFinalizing).
- **Benefit**: A recording that fails at once ends at once with the 'recording interrupted' message, as the watchdog KDoc intends. The overlay does not stay on 'Recording...', and the next key press is typed, not swallowed.
- **Evidence**: AudioRecorder.kt:134 `if (recordingJob != null) completion else null`. The job body clears recordingJob at :421 and :464. Early loop exits: :301-305 (write IOException), :328-332 (ERROR_DEAD_OBJECT), :333-336 (other read errors). recordingScope is Dispatchers.IO (:74), so the body runs in parallel with the main thread. - **Safety**: Changes only the return condition of a getter that has one caller. ## Areas in good shape
- Background work: no wake locks, alarms, WorkManager, JobScheduler or foreground services. The only polling is the 80 ms meter ticker. It runs only during a recording and stops when no telemetry is available.
- AI managers (Voice, Text Fix, Translate): LatinIME.onDestroy cancels their scopes. Hide and finish-input cancel running work. A token for each request drops late results. One 'request cancelled' toast shows.
- Typing hot path (fork code): the lock state and the IME list are cached, so a key press makes no binder IPC. getTextBeforeCursor builds only the tail. One Rect is reused for each draw. The code checks the clip description before it copies the clip.
- Async suggestions: the text cache is locked, the worker has an exception barrier, sequence numbers drop stale strip updates, and the HandlerThread quits in onDestroy.
- Network: the code drains bodies before disconnect. Retries have a deadline budget. The code does not resend audio after a read timeout. Response and error reads have size caps. A cancel never uploads again. Exceptions carry no key.
- Cold start: fork work runs off the main thread. The vault warm-up runs only when an AI feature is on (PERF-002).
- Audio: 40 ms reads go straight to disk. Stop, WAV finalize and the orphan sweep run off the main thread. OnDeviceRecognizer has a session guard and a decode timeout.
- SecretStore: a decrypt or vault failure becomes 'no key', not a crash. Vault prefs are in device-protected storage.
- Overlays: animators and the ticker stop on detach. The overlay state comes back on a recreated strip.
- R8 and packaging: optimize profile, minify on, only 3 app keep rules, no -dontoptimize. The PERF-001 excludes are in place. The four ABIs and resource shrinking off are owner decisions (dc9f8883).
- Dependencies: each runtime library is used. The network code uses HttpURLConnection and org.json, with no HTTP library. security-crypto is gone since 7.13.2.
- Dead code in fork code is close to zero. All 10 drawables that the fork added are used.
- Settings, wizard and clipboard UI: strings resolve lazily, list keys are stable, touch targets are 48 dp, dialogs keep their state on rotation, secrets never go to saved state, and empty and no-match states exist.
- Crash log: the only crashes were DEV-001/002, which 7.13.1/7.13.2 fixed. The phone showed no new crash or ANR.
